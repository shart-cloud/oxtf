## Design

**A new crate, `crates/tf_plan`** (refs.rs 235 lines, lib.rs 1,061 lines after rustfmt, tests 324 lines), depending on `tf_semantic`, `tf_eval`, `tf_schema`, `tf_linter` and `serde_json`. Why not a module of `tf_semantic`:

- It is a second *front end* that produces the semantic layer's output type. It is not part of the HCL semantic layer. This is the oxc split: parsers and front ends are separate crates feeding one model.
- It needs `tf_semantic` itself: the source directory is analysed with `analyze_module` to recover spans (below), so living inside `tf_semantic` would make the HCL analyser call its own consumer.
- It owns the `scan_plan` entry point, which builds a `tf_linter::ScanResult`. `tf_semantic` must not depend on `tf_linter`.
- The cost of the split is nil: `tf_cli` gained one dependency and the HCL path is untouched.

**Pipeline** (`tf_plan::load_plan`):

1. Parse the JSON with `serde_json`. Reject inputs with no `format_version`, or with neither `planned_values` nor `resource_changes`. Warn on `errored: true` (`plan-errored`) and on `format_version` other than 1.x (`plan-format`). The plan file is registered in the scan's `FileTable` so it can serve as a fallback span target.
2. Resources:
   - managed resources come from `resource_changes[].change.after`, with `after_unknown` and `after_sensitive`. Pure `delete` and `forget` actions are skipped (nothing will exist).
   - data sources come from `resource_changes` (deferred reads) and from `prior_state` (read during planning; `aws_iam_policy_document` lands here).
   - `module_address` and `index` give the module instance and the instance key. Addresses are the plan's own (`aws_security_group.ssh[0]`, `module.store.aws_s3_bucket.b["a"]`).
3. Configuration index: `configuration.root_module` and, recursively, `module_calls.<name>.module`, keyed by the module path without instance keys, give each resource's `expressions`.
4. Body construction is schema-guided (`tf_schema::lookup`): members the provider schema declares as nested *blocks* become `model::Block`s, and everything else becomes `model::Attr`. So `ingress` on `aws_security_group` is an attribute holding a list of objects, as in the HCL model (attributes-as-blocks).
5. Module instances are every `module_address` seen, plus its ancestors, with `parent` links. `dir`, `symbols`, `module_calls` and `references` come from the source analysis of that module when available.
6. `scan_plan` runs `Linter::run(&analysis)`, the same call `scan_with` makes per root, and fills `ScanResult` / `ScanStats`, so `render_finding` and `result_json` work unchanged.

## Value mapping (plan to lattice)

| plan JSON | lattice | why |
|---|---|---|
| known value in `after` | `Known` (containers recursively), with no provenance below the attribute | as in the HCL model, nested values carry only their own steps; `child_of` joins the attribute step |
| node marked `true` in `after_unknown`, attribute **set in configuration**, expression references exactly one resource attribute | `Unknown { Computed { resource: <module prefix><referenced address>, key, attr } }` | this is what the HCL evaluator yields for `aws_s3_bucket.data.id`, so `aws-s3-public-access-block`'s join (`Origin::Computed` on the bucket's `id` / `bucket`) works unchanged |
| same, but references give a resource without an attribute (plan JSON records `aws_s3_bucket.b[each.key].id` as `["aws_s3_bucket.b", "each.key"]`) | the origin of the same attribute in the **source model** if that is `Computed` on the same resource; else `Unknown{Other}` | the attribute after a dynamic index is lost in plan JSON. The HCL evaluator saw the whole traversal. Found by `plan_cases/module_count_sensitive` (before this fallback all three S3 findings in the child module were suppressed as "maybe" matches) |
| `after_unknown`, set in configuration, other references (several resources, `module.x.out`) | `Unknown { Other("unknown until apply (depends on ...)") }` | a "maybe" for the S3 join: suppressed, as in source |
| top-level attribute `after_unknown`, **not in configuration** | **omitted from the body** | provider-computed (`id`, `arn`) or optional+computed left unset. The HCL model has no such attribute either, so `value_or_default` applies the defaults overlay. Without this, `gcp-storage-uniform-access/fail_absent` would be silent on the plan: `uniform_bucket_level_access` is `(known after apply)` there |
| nested `after_unknown` node | `Unknown { Computed { own resource, attr: "<attr>[i].x" } }` | |
| `null` in `after` | `Known(Null)` | `value_or_default` treats null as unset, as for source |
| known value **not** in configuration (`force_destroy = false`, `region`) | kept as `Known` | the plan's planned value is better information than the overlay. Provenance label: `<addr> <attr> not set in configuration: planned <v>` |
| `after_sensitive` | **kept `Known`**; the attribute's provenance label says `(sensitive)` and omits the value; variable steps omit the value when the variable is declared `sensitive` (`configuration.root_module.variables.<n>.sensitive`) or the attribute is sensitive | rules need the value (a sensitive CIDR is still open). `terraform show -json` already carries sensitive values in clear text (`grep -c not-a-real-password fixtures/plan_cases/module_count_sensitive/plan.json` → 4), so hiding them in the model would protect nothing and would lose findings. Test `plan_case_module_count_sensitive` asserts no label contains the value |
| `Tainted`, `OneOf` | never produced | terraform requires a value for every variable and resolves every conditional and `for_each` before planning. A plan can therefore not give *conditional* severity: it is one point of the source's value space |

`existence` is always `True` (instances are explicit in a plan); `count` / `for_each` are `None`.

## How source spans are recovered

Plan JSON has no positions. The source directory (`--source DIR`, or by default the plan file's directory if it contains `.tf` files) is analysed with the existing HCL front end (`tf_semantic::analyze_module`) and used **only as a span index**. Values always come from the plan. This reuses module assembly, local-module following (`module.store` → `modules/store/main.tf`) and the symbol table, instead of a second, ad-hoc `.tf` walker.

| plan element | span |
|---|---|
| resource `address` (module path, type, name, key) | `resource` / `data` block header of the source instance with the same key if the source expanded it, else of the representative instance, in the source module with the same key-stripped address |
| top-level attribute | the source `Attr` span (an attribute, or the first block for attributes-as-blocks / `dynamic`), else the nested block's body, else the resource header (attribute not written in source) |
| nested-block attribute | the matching (i-th) source block's attribute, else the block |
| reference `var.x` in the attribute's `expressions.*.references` | `variable "x"` block; label `variable x = <plan value> (plan input)` for root variables |
| reference `local.y` | the `locals` entry (`SymbolRef::Local` span) |
| reference `aws_s3_bucket.data.bucket` | that resource's `bucket` attribute (or header); the step carries `resource = "aws_s3_bucket.data"` like the HCL model's attribute steps |
| resource not found in source (no source, remote module) | its `"address": "<addr>"` entry inside the plan JSON file, plus an Info diagnostic `plan-unmapped` (test `plan_without_source_points_into_plan_json`) |

Attribute steps use the same label shape as the HCL front end (`<address> <attr>`), so rule messages that quote the deciding step are identical on both inputs. The fixture test checks message equality for every non-variant case. There is one allowed, intended difference: in `fail_block_attrs_absent_default_false` the plan knows the provider's planned `false` where the source falls back to the overlay.

**Where plan and source output differ** (findings equal, presentation not):

- **Primary span granularity.** For `aws-sg-open-ssh` the primary location is the `ingress` block (`main.tf:6:3`) rather than the `cidr_blocks` line the source scan points at (`main.tf:10`). Plan values below a top-level attribute have no per-path spans (see gaps).
- **Provenance depth.** Only *direct* references of the attribute's expression become steps. `fail_tfvars_through_local` on the plan shows `local.ssh_sources -> aws_security_group.admin ingress`. The source shows `terraform.tfvars -> variable admin_cidr -> local.ssh_sources -> ...ingress.cidr_blocks`. The plan's `configuration` does not include `locals`, so `local.ssh_sources → var.admin_cidr` is not visible in plan JSON.
- **`-var` values are recorded as strings** in the plan's `variables` (`block_public = "false"`), and the label quotes them as recorded. Planned resource values are typed (`false`).

## What had to change

- **Rules, engine, model, evaluator, schema: nothing.** Each case that first looked like it needed a rule change was solved in the plan→model adapter instead:
  - optional+computed attributes left unset → omitted, so the overlay applies (needed for `gcp-storage-uniform-access/fail_absent`);
  - unknown join keys → `Origin::Computed` rebuilt from `configuration` references;
  - dynamic-index references → origin taken from the source model;
  - attribute step labels in the HCL shape, so the S3 rule's message (which quotes the deciding step) is unchanged.
- `tf_cli`: `--plan` / `--source`, and the directory scan / printing split into `scan_dirs` / `print_result` (additive; existing CLI tests pass).
- Workspace: `tf_plan` added to `[workspace.dependencies]`.

## Scope cuts and known gaps

| cut / gap | why / impact |
|---|---|
| Nested-path spans: a value below a top-level attribute (`ingress[0].cidr_blocks`) points at the attribute or block, not the nested line | Mapping a planned list element back to the i-th written or `dynamic`-expanded block needs the source evaluator's element provenance joined with plan values. Timebox. Findings are unaffected, only the caret position is coarser |
| Provenance is one hop (direct `var.` / `local.` / resource references), not the full tfvars → variable → local chain | plan JSON has no `locals` and no tfvars origin. A real build would merge the source model's chain when the source value equals the plan value |
| Child-module variables have no values in plan JSON | their `VariableInfo.value` is `Unknown{Other("module input (not recorded in plan JSON)")}`; labels name the variable without a value |
| Sensitive values stay `Known` | labels are redacted, but a rule message that renders the witness (e.g. `aws-sg-open-ssh`'s `from <cidr>`) would print a sensitive CIDR. A real build needs a sensitivity bit on `Value` that `render` respects. None of the fixtures exercise this |
| Only create-only plans tested (fresh state, `-refresh=false`) | updates, replaces, `resource_drift`, `deferred_changes`, `moved` and import were not generated: that needs real state or credentials. The reader handles `update` / `replace` like `create` (it reads `after`) and skips pure `delete` / `forget`, but this is untested |
| Remote modules | handled by fallback (`plan-unmapped`, JSON spans); not tested against a real registry module (no fixture fetches modules) |
| Plan JSON `format_version` 1.2 only (terraform 1.16.6) | other 1.x versions are accepted with no warning; 0.x / 2.x warn |
| No `tfscan` (Python) entry point for plans | W6 is done and frozen; adding `tfscan.scan_plan` is about 20 lines of PyO3 but was not in the W5 checklist |
| No corpus-scale plan run | corpus modules need real variables, credentials and data-source reads to plan. The 34 fixtures + 1 plan case are the evidence |
| Plan generation is slow | 34 plans took 10m09.754s and 9m35.764s wall (two full runs; about 17 s per case, dominated by `terraform init` + provider start-up; a CPU-heavy process from another session was running during the first run). Tests use the committed JSON and need no terraform |

## Reproducing the plans offline

`fixtures/plans/generate.sh [WORK_DIR]` (default `/tmp/claude-0/w5`):

- copies each case (the fixtures are not edited), deletes `EXPECT`, and adds `zz_w5_providers.tf`. This is a plain file, not an `_override.tf`: override files only merge into existing blocks, and the fixtures have no `terraform` / `provider` blocks. It pins `hashicorp/aws 6.68.0` and `hashicorp/google 8.7.0`. The `aws` provider gets `region = "us-east-1"`, `access_key = secret_key = "x"` and all four `skip_*` flags. The `google` provider gets `project = "x"` and `credentials = file("fake-sa.json")`, a service-account JSON with a freshly generated throwaway RSA key that is not committed and not in the plan output.
- runs `terraform init -plugin-dir=/opt/tftools/plugin-cache`, `terraform plan -refresh=false -out=tfplan [-var ...]` and `terraform show -json tfplan`, then pretty-prints with sorted keys.
- regenerating changes only the `timestamp` field. After the second full run, `diff -r` against the first showed 68 changed lines, all `timestamp` (34 files × 2 lines).

**Google worked offline**: all three gcp plans succeeded, and no cut was needed. **Network**: AWS and Google endpoints *are* reachable through the agent proxy here (`curl https://sts.us-east-1.amazonaws.com/` → 302). To show the plans do not need the network, three cases (S3, GCS, `aws_iam_policy_document`) were re-planned with `HTTPS_PROXY` / `HTTP_PROXY` pointed at a closed port. All three exited 0. `aws_iam_policy_document` is evaluated locally by the provider; no fixture uses an API-backed data source.
